# ML Rework Classifier — Dataset, Training, and Integration Guide

This folder contains everything used to build and validate the Stage-2 ML
classifier described in the project proposal: a synthetic-but-realistic PR
corpus with known ground truth, the scripts that generated and trained
against it, and the resulting trained model. It's written for whoever wires
the model into the live app — that hasn't been done yet on purpose, so you
can review the approach and own the integration.

## Compatibility check (read this first)

Before wiring anything in, two things were verified:

1. **The trained model's expected feature order exactly matches
   `ReworkFeatures`** in `backend/app/services/rework_detection/features.py`
   (13 fields, same names). Verified by direct comparison — see
   `backend/app/services/rework_detection/artifacts/metadata.json`'s
   `feature_order` list against the `ReworkFeatures` class definition.
2. **The model loads and scores correctly** via `joblib.load(...)` +
   `.predict_proba(...)` on a real `ReworkFeatures` instance — confirmed live,
   no errors, no dependency issues.

**Two real prerequisites — both now resolved as their own clean PRs:**

- **The `disposition` column on `rework_events`.** The model's
  `author_historical_rework_rate` feature is computed live from
  human-confirmed disposition reviews (`queries.py`'s
  `get_author_historical_rework_rate` / `get_global_rework_rate`). Shipped in
  `feature/reviewer-disposition` — merged.
- **The `ReworkFeatures` / `compute_rework_features()` code itself**
  (`backend/app/services/rework_detection/features.py`) and the 4 new
  qualifying signals wired into `rework_detector.py`. This is what the model
  was actually trained against, so it has to exist in the app before the
  model is usable at all. Shipped in `feature/rework-feature-extraction`
  (based on the disposition branch) — conflicts with `main` resolved and
  fully re-verified (27/27 tests, `recompute`, and the `/features` endpoint
  all confirmed working post-merge-conflict-resolution). Check whether this
  PR has actually been clicked-merged into `main` yet before assuming it's
  there — as of writing it was verified and ready, one click away.

Once both are actually on `main`, the classifier wiring described below is
the only remaining piece.

## What's in this folder

| File | What it does |
|---|---|
| `generate_large_seed.py` | Generates the synthetic PR corpus (see "How the dataset was built" below). Writes to `data/seed/*.json` (replacing whatever's there) and `data/training/ground_truth_pairs.json` / `authors.json`. |
| `train_classifier.py` | Loads that seed data, runs the **real** `compute_rework_features()` against every same-repo/right-order/within-90-days candidate pair, joins with ground truth, writes `data/training/real_candidate_features.csv`. |
| `evaluate_classifier.py` | Trains and compares Logistic Regression, Random Forest, Gradient Boosting, and an MLP on that CSV, with a proper grouped train/test split. Prints ROC-AUC, PR-AUC, and feature importances. |
| `train_final_model.py` | Trains the final Gradient Boosting model on the *entire* labeled dataset (no held-out split — that's what `evaluate_classifier.py` is for) and saves it to `backend/app/services/rework_detection/artifacts/`. |
| `generate_report.py` | Same model comparison as `evaluate_classifier.py`, but saves presentation-ready figures (ROC curve, precision-recall curve, confusion matrix, feature importances) and a markdown summary to `docs/ml-classifier/` instead of just printing to the terminal. |

Regenerating from scratch, in order:
```bash
cd ml-classifier
../backend/.venv/bin/python generate_large_seed.py --seed 7
../backend/.venv/bin/python train_classifier.py
../backend/.venv/bin/python evaluate_classifier.py   # optional — just prints a comparison report
../backend/.venv/bin/python train_final_model.py
../backend/.venv/bin/python generate_report.py       # optional — figures + report for docs/ml-classifier/
```
(Needs `backend/.venv` set up via the normal `uv sync` in `backend/` — `numpy`/`pandas`/`matplotlib` are dev deps, `scikit-learn`/`joblib` are real runtime deps of the app now.)

## How the dataset was built

484 synthetic pull requests across 8 repos, 4 teams, 32 authors — generated
using the app's **real** `PullRequest`/`PullRequestFile` models and real
`classify_file_risk`/`is_test_file` functions, so every file path was
validated against the actual detector logic, not a parallel simulation.

Each AI-generated PR has a probability of spawning a genuine rework
follow-up (15% base rate, +12% if it touched a high-risk file, adjusted by a
hidden per-author "how careful is this person" trait that's never exposed as
a feature — only observable through outcomes over time, the same way it
would work on real data). Follow-ups get real corrective-language text,
overlapping files, and — 45% of the time — an explicit `Fixes #N` reference;
15% share an unlinked issue number; the remaining ~40% have no explicit link
at all, so the model can't just cheat off an obvious signal.

Result: **53 genuine rework pairs** out of 225 AI-generated PRs (~23.6%).
Considering every same-repo, right-order, within-90-days candidate pair (the
actual training universe): **13,952 pairs, 53 of them real (0.38%)** — a
realistic, heavily imbalanced problem, not an artificially balanced toy one.

**Known limitations, worth repeating to whoever reviews this:**
- The PR text is template-generated — believable, not indistinguishable from
  real engineer writing.
- All 8 repos share the same made-up vocabulary; a real org's teams would
  write in genuinely different domain language.
- The "how careful is this author" trait driving rework outcomes is entirely
  invented. The *mechanism* for learning from it (a live historical rate,
  computed from actual disposition reviews) is real and would work the same
  way on real data — the underlying cause it's modeling here is not.
- No line/diff-level data exists anywhere (deliberately out of scope, see
  `docs/detection-and-estimates.md`).

## Model results

Tested on a held-out set the models never saw (4,081 pairs, 9 of them real),
split so no PR's rows leak across train/test:

| Model | ROC-AUC | PR-AUC | Caught in top 100? | Precision | Recall |
|---|---|---|---|---|---|
| Logistic Regression | 0.995 | 0.802 | 8/9 | 0.222 | 0.889 |
| Random Forest | 0.9985 | 0.760 | 9/9 | 0.800 | 0.889 |
| **Gradient Boosting** ✅ deployed | 0.998 | **0.879** | 9/9 | 0.800 | 0.889 |
| MLP | 0.994 | 0.796 | 8/9 | 0.500 | 0.778 |

Gradient Boosting and Random Forest are nearly tied; Gradient Boosting wins
on PR-AUC, the metric that matters most given how rare the positive class is
(ROC-AUC is known to look deceptively good under heavy imbalance like this).

## Wiring it in

**A full reference implementation already exists** on the working branch
this was built on (not yet split into its own clean PR — that's intentional,
so you can review it, change it, or redo it rather than silently inherit it).
Rather than instructions for work that isn't done, here's exactly what's
already there and where, so you can decide what to keep:

1. **`classifier.py`** (`backend/app/services/rework_detection/`) —
   `predict_rework_probability(features: ReworkFeatures) -> float`. Loads the
   model lazily, reads `feature_order` from `metadata.json` so it's robust to
   `ReworkFeatures` changing field order later, returns a plain float.
2. **`ml_rework_probability` field** already added to `ReworkCandidate`
   (`models.py`), `ReworkEvent`/`ReworkEventDetailEvent` (`schemas.py`), and a
   matching `ml_rework_probability REAL NOT NULL DEFAULT 0` column on
   `rework_events` (`001_init.sql`).
3. **`queries.py`** — `get_global_rework_rate()` and
   `get_author_historical_rework_rate()` compute the live historical-rate
   feature from disposition data; `ml_rework_probability` is included in
   `get_rework_events()`/`get_rework_event_detail()` reads, and — unlike
   `disposition`/`root_cause_label` — it **is** refreshed in
   `replace_rework_events()`'s `ON CONFLICT` clause, since it should always
   reflect the latest model run, not a frozen human edit.
4. **`rework_detector.py`** — `generate_rework_candidates()` computes
   `author_historical_rework_rate` per candidate, builds `ReworkFeatures` via
   `compute_rework_features()`, then calls `predict_rework_probability()` and
   attaches the result to each `ReworkCandidate`.
5. **Frontend** — a color-coded "ML Score" badge (red ≥70%, yellow ≥40%,
   gray below) on both the dashboard list (`page.tsx`) and the detail page
   (`[reworkId]/page.tsx`), matching the existing severity/disposition badge
   style already in those files.

All of the above was manually verified end-to-end: reseeded the DB, ran
`recompute`, confirmed the highest-scored candidates were all genuine and the
lowest-scored were all false positives, and confirmed the badges render
correctly in the browser. It hasn't been committed as its own PR yet — if you
pick this up, treat it as a draft to review, not a fait accompli.

**Retraining:** whenever the seed dataset changes meaningfully, re-run
`train_classifier.py` then `train_final_model.py` to refresh the deployed
artifact. There's no automatic retraining pipeline yet — it's a manual step.
